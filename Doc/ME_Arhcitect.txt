private bool EvaluateMediaQuery(string mediaText, double vpW, double vpH)
{
    // e.g. "screen and (min-width: 768px) and (max-width: 1200px)"
    var conditions = ParseMediaConditions(mediaText);
    return conditions.All(c => c switch {
        ("min-width", var px) => vpW >= px,
        ("max-width", var px) => vpW <= px,
        ("min-height", var px) => vpH >= px,

## Testing Strategy Summary

Since this is a solo project with no CI, no unit test framework, and an ARM device
as the primary target, testing has to be low-friction and high-signal.

### The 5-minute post-session ritual

After every session, before committing:

```
1. Build (0 errors required — never commit with errors)
2. Navigate to about:test
3. Scroll to Section C (JS tests) — note pass/fail count
4. Scroll to Section B (CSS tests) — visually check T-C-001..010
5. Navigate to T-S-001 (DuckDuckGo) — search box visible? ✓/✗
6. Navigate to T-S-004 (httpbin.org/html) — text readable? ✓/✗
7. Open DevTools Debug tab — any new [ERROR:] or [WARN:] markers?
8. Add one line to Doc/Perf_Baseline.md: date, build, pass count
```

If step 6 fails after passing before, **stop and fix before moving on**.

### Three layers of testing

```
Layer 1: about:test (automated, in-browser)
         HTML structure × CSS properties × JS behavior
         Runs on every launch — takes 30 seconds
         Catches: parser regressions, CSS cascade breaks, NiL.JS regressions

Layer 2: Site matrix (manual, weekly)
         T-S-001 through T-S-010 — 10 target sites
         Capture screenshots, compare to reference
         Catches: real-world rendering regressions

Layer 3: ARM device (manual, before major releases)
         Test on actual Lumia 950 (if available)
         Focus: performance (Snapdragon 810 ≠ x86 emulator), touch targets
         Catches: ARM-specific crashes, performance regressions
```

### What each test section covers

**Section A (T-H-xxx) — HTML Parser:**

Tests that the HTML tokenizer and tree builder produce correct DOM structure.
If T-H-003 (table with colspan) breaks, look at `HtmlParser.cs` and `TableRenderer.cs`.
These tests are almost never wrong — HTML parsing is stable.

**Section B (T-C-xxx) — CSS Engine:**

Tests that `CssLoader.cs` + `CssComputed.cs` + `DomBasicRenderer.cs` correctly
apply properties. If T-C-002 (flexbox) breaks after a cascade change, look at
`CascadeIntoComputedStyles` and `FlexPanel`.
Add a new T-C-xxx case before implementing any new CSS property.

**Section C (T-J-xxx) — JavaScript Runtime:**

Tests that NiL.JS + JsDomElement correctly handle JS operations.
A regression here usually means a NiL.JS change broke something.
Known-broken tests are marked `KNOWN-FAIL` — don't "fix" these by changing the test.

**Section F (T-F-xxx) — NiL.JS Compatibility Matrix:**

Static reference. Each row is a JS feature. Green = works, Yellow = partial,
Red = known unsupported (stop trying to fix these in main sessions).

## Notes for Solo Development (updated)

**The `in` operator is the last trivial NiL.JS fix.** After 3.18, resist the urge to
dive back into NiL.JS for 5 sessions. Every NiL.JS session costs 3× more time than
planned (regression risk + debugging + re-test).

significantly better. A morning on NiL.JS makes one site fail less silently.

**Know when a site is a fair test.** httpbin.org/html and text.npr.org are fair tests
for a museum browser — they're text-heavy sites where your renderer should shine.
Nokia Design Archive is an unfair test — it's a D3.js-heavy SPA that needs private
class fields, Canvas API, and full SVG DOM. Don't measure success against unfair tests.

**The POOR mode is your reputation manager.** If a site causes an exception, POOR mode
should always be able to show at least readable text. Users will appreciate graceful
degradation over hard crashes every time.

**Ship v1.0.** A released "museum-stable v1.0" that renders 5 sites correctly is more
valuable than an unreleased browser that almost renders 50 sites. Retro projects gain
momentum from tangible releases.

All five blockers in the diagram above must be solved, and they must be solved in order — you can't test #3 (XAML rendering) until #2 (SVG DOM creation) works, and you can't test #2 until #1 (private class fields) is fixed.

Question 2 — How long, solo with good AI?
Solo without AI: 10–16 weeks. Private class fields alone is a week of NiL.JS parser and runtime work, and it carries regression risk every time you touch the parser (session 3.13 taught that lesson painfully).
Solo with a good AI programmer (Claude, GPT-4 in agentic mode): realistically 3–5 weeks. Here's why AI helps dramatically here: steps 2–4 are mostly mechanical code that follows clear patterns. Once you know that <circle cx="50" cy="50" r="20"/> should become XAML <Ellipse Canvas.Left="30" Canvas.Top="30" Width="40" Height="40"/>, an AI can generate all 15–20 SVG element types in one session. The hard parts that stay hard even with AI are NiL.JS private fields (deep parser surgery with regression risk) and the DOM event bridge (requires understanding the existing JS engine architecture well).
A realistic breakdown with AI assistance: 4–7 days for private fields, 2–3 days for SVG DOM creation, 3–4 days for XAML SVG renderer, 3–4 days for DOM events, 1–2 days for getBoundingClientRect. That's 13–20 working days, call it 4 weeks if you count testing and debugging between steps.

Question 3 — Is XAML rendering suitable, or should you switch to Skia?
XAML is suitable and you should not switch to Skia. This is the most important of the three answers.
The rendering primitive is not the bottleneck. D3.js creates SVG elements via JavaScript DOM operations. Regardless of whether you render those elements with XAML, SkiaSharp, or Win2D, you still need to solve the exact same five blockers — private class fields, SVG DOM creation, rendering each element type, DOM events, and getBoundingClientRect. Skia doesn't help with any of them.
Where SkiaSharp would actually help is if you were rendering static SVG images (like icons or embedded illustrations). It's already partially in your codebase for that purpose and that's the right scope for it. For D3.js dynamic SVG, the path is: JavaScript creates DOM nodes → JsDomElement creates LiteElement SVG nodes → a new SvgRenderer.cs converts each node to its XAML equivalent (Ellipse, Line, Path, TextBlock, XAML Canvas for groups) at render time. This keeps the architecture consistent with everything else in the engine.
The one place where Win2D (Microsoft's Canvas 2D for UWP) could be useful is if D3 is configured to use a Canvas element instead of SVG — some D3 layouts support both. But the Nokia Archive specifically uses SVG, so Win2D doesn't help here either.
The short version: don't change the renderer. Fix the JS engine and build the SVG→XAML bridge. That's the only path.

Вопрос 1. Можете ли вы открыть только архив Nokia?

Вопрос 2. Как долго длится соло с хорошим ИИ?
Соло без ИИ: 10-16 недель. Одни только поля частного класса - это неделя обучения. Вмешательство в работу синтаксический анализатора и среды выполнения NiL.JS сопряжено с риском регрессии каждый раз, когда вы этому прикасаетесь (урок 3.13 был болезненным).
В одиночку с хорошим программистом с искусственным интеллектом (Claude, GPT-4 в режиме агента): реально 3-5 недель. Вот почему искусственный интеллект здесь очень помогает: шаги 2-4 - это в основном механический код, который следует четким шаблонам. Как только вы узнаете, что <circle cx="50" cy="50" r="20"/> должен стать XAML <Ellipse Canvas.Left="30" Canvas.Top="30" Width="40" Height="40"/>, искусственный интеллект может сгенерировать все 15-20 типов элементов SVG за один сеанс. Сложные части, которые остаются сложными даже при использовании искусственного интеллекта, - это  приватные поля NiL.JS (операция глубокого синтаксического анализа с риском регрессии) и DOM event bridge (требует хорошего понимания существующей архитектуры движка JS).
Реалистичная разбивка с помощью искусственного интеллекта: 4-7 дней для частных полей, 2-3 дня для создания SVG DOM, 3-4 дня для рендерера XAML SVG, 3-4 дня для событий DOM, 1-2 дня для getBoundingClientRect. Это 13-20 рабочих дней, то есть около 4 недель, если считать тестирование и отладку между этапами.

Вопрос 3 — Подходит ли рендеринг на XAML или вам следует перейти на Skia?
XAML подходит, а на Skia переходить не следует. Это самый важный из трех ответов. Примитив рендеринга не является узким местом. 
D3.js создает SVG-элементы с помощью DOM-операций JavaScript. Независимо от того, визуализируете ли вы эти элементы с помощью XAML, SkiaSharp или Win2D, вам все равно нужно решить те же самые пять проблем: поля закрытого класса, создание SVG DOM, рендеринг каждого типа элемента, события DOM и getBoundingClientRect. Skia не помогает ни с одним из них.
Где SkiaSharp действительно помог бы, так это при рендеринге статических изображений в формате SVG (например, значков или встроенных иллюстраций). Частично он уже есть в вашей кодовой базе для этой цели, и это подходящая область для него. Для D3.js динамический SVG, путь таков: JavaScript создает узлы DOM → JsDomElement создает узлы LiteElement SVG → новый SvgRenderer.cs преобразует каждый узел в его эквивалент в XAML (эллипс, линия, путь, текстовый блок, холст XAML для групп) во время рендеринга. Это позволяет поддерживать архитектуру в соответствии со всем остальным в движке.
Единственное, где Win2D (Microsoft Canvas 2D для UWP) может быть полезен, — это если D3 настроен на использование элемента Canvas вместо SVG - некоторые макеты D3 поддерживают и то, и другое. Но в архиве Nokia специально используется SVG, поэтому Win2D здесь тоже не поможет.
Короткая версия: не меняйте средство визуализации. Исправьте движок JS и создайте мост SVG→XAML. Это единственный путь.
